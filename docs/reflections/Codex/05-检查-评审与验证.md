# 检查、评审与验证

“Codex 说完成了”不是验证证据。一个完整的工作流应该把验证拆成：状态检查、差异检查、自动化测试、运行时检查、代码评审和人工确认。

## `/diff`：先看实际改了什么

```text
/diff
```

重点检查：

- 是否改到了任务范围之外的文件；
- 是否混入格式化、生成文件或临时文件；
- 是否修改了配置、密钥或部署文件；
- 是否存在看不懂的删除、重命名或大段重写；
- 是否把用户原有的未提交修改覆盖了。

在终端中也可以配合：

```bash
git status --short
git diff --stat
git diff
```

不要只看 Codex 的总结，要看 Git 的真实状态。

## `/review`：让它换一个角色

```text
/review
```

可以把审查重点写进后续要求：

```text
请重点检查：
1. 是否引入数据丢失风险；
2. 是否有未处理的错误分支；
3. 是否破坏移动端布局；
4. 是否缺少覆盖回归场景的测试。
```

官方说明中，Codex 的内置 `/review` 会检查 Git checkout 中的改动，并报告优先级较高的问题；它和 GitHub Pull Request 的 Code Review 集成不是同一个入口。

## `/status`：验证环境，而不只是看进度

```text
/status
```

用它确认：

- 当前项目和工作目录；
- 当前模型和推理档位；
- 本地还是云端执行；
- 当前审批和沙箱策略；
- 上下文是否接近上限；
- 会话是否仍在正确的分支。

## `/ps` 和 `/stop`：管理后台进程

启动开发服务器、测试监控或构建进程后：

```text
/ps
```

它可以查看后台终端及最近输出。任务结束后：

```text
/stop
```

停止当前会话启动的后台终端。若你需要保留 dev server 供浏览器检查，不要过早执行 `/stop`。

## 验证层级

### 第一层：静态检查

```bash
git status --short
git diff --check
```

### 第二层：项目脚本

```bash
pnpm lint
pnpm test
pnpm build
```

根据项目实际脚本选择，不要机械执行不存在的命令。

### 第三层：运行时验证

启动项目后检查：

- 页面或 API 是否能访问；
- 浏览器控制台是否有错误；
- 主要交互是否可用；
- 移动端和桌面端是否都正常；
- 网络失败、空数据和加载状态是否合理。

### 第四层：视觉验证

视觉任务应固定：

- 视口宽高；
- 浏览器缩放比例；
- 字体和资源加载状态；
- 截图时机；
- 动画是否需要等待或关闭。

不要凭“看起来差不多”结束。应该截图、对比、定位差异，再做下一轮修改。

### 第五层：人工验收

人工确认：

- 业务意图是否正确；
- 是否保留了用户原有行为；
- 文案、链接、权限和数据是否符合预期；
- 是否有不能从源码推断的设计决策。

## 推荐的完成提示

```text
现在进入验证阶段：
1. 运行项目已有的 lint、test、build 脚本；
2. 检查 git diff 和 git status；
3. 如果是前端任务，启动开发服务器并验证桌面、移动两个视口；
4. 把每个验证命令、结果和未解决风险列出来；
5. 不要把没有实际运行的命令写成“已通过”。
```

## `/feedback`

遇到 Codex 产品本身的问题时：

```text
/feedback
```

它用于提交反馈，可能包含诊断日志。提交前检查日志里是否有不应该分享的路径、域名、项目名或敏感信息。

官方参考：[Code review](https://learn.chatgpt.com/docs/code-review)、[Developer commands](https://learn.chatgpt.com/docs/developer-commands)。
