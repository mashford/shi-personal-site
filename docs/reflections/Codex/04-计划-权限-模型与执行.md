# 计划、权限、模型与执行

Codex 的质量不只取决于模型名称。一个复杂任务如果上下文不清、权限不合适、没有验证步骤，即使使用更强的模型也可能做出不可靠的修改。

## `/plan`：解决“还没想清楚就开始改”

示例：

```text
/plan
```

或：

```text
/plan 分析这个项目的部署流程，找出可能导致生产环境白屏的路径，先不要修改文件
```

计划阶段应该回答：

- 入口文件在哪里？
- 当前行为和期望行为是什么？
- 哪些事实已经确认，哪些只是猜测？
- 需要改哪些文件？
- 如何验证修改真的生效？
- 有没有不可逆或高风险操作？

好的后续提示：

```text
按这个计划实施。每改一个阶段都运行对应验证；如果发现证据不足，不要猜，停下来告诉我需要什么。
```

## `/goal`：解决“做着做着忘了完成标准”

```text
/goal 完成 React 页面复刻：1440px 和 390px 截图都通过，交互可用，未知视觉差异必须列出而不能臆造
```

目标要包含完成条件。比如下面两种写法的区别：

```text
# 太模糊
/goal 把页面做好

# 可验证
/goal 在桌面和移动视口验证页面；运行 pnpm build；检查主要交互；把剩余差异和无法确认的部分写进报告
```

## `/model` 和 `/reasoning`

```text
/model
/reasoning
```

`/model` 选择当前会话的模型；`/reasoning` 调整推理强度。具体可选模型和档位取决于账号、产品版本和当前环境。

一般原则：

| 任务 | 选择思路 |
| --- | --- |
| 单文件小修复、改文案 | 偏快速、低推理 |
| 普通 Bug、测试、局部重构 | 中等推理 |
| 跨文件架构、复杂调试、视觉还原 | 更高推理，并要求验证 |
| 长时间自主工作 | 高推理，但必须设置清晰完成标准 |

更高推理不能弥补缺失的设计稿、报错、运行环境或验收标准。

## `/fast`

```text
/fast
```

当当前模型提供 Fast 服务层时，它可以在速度和资源使用上做取舍。它不是“让模型变聪明”，也不是所有账号和模型都有。

如果任务需要精确还原、跨文件判断或多轮验证，不要只因为快就跳过检查。

## `/permissions`

```text
/permissions
```

它控制 Codex 在当前聊天中哪些操作可以直接执行，哪些操作需要先询问。不同版本可能展示不同的审批预设，例如只读、需要确认或更自动化的模式。

使用建议：

| 阶段 | 建议 |
| --- | --- |
| 了解项目、规划 | 只读或严格审批 |
| 修改当前项目 | 允许工作区写入，但保留危险操作确认 |
| 运行测试和构建 | 根据命令风险逐步批准 |
| 数据库、部署、删除、推送 | 保留人工确认 |

不要把“自动批准”理解成“操作一定安全”。它只是改变了谁在执行前确认。

## `/approve`

```text
/approve
```

当自动审查拒绝了最近一次操作时，用它批准一次重试。使用前要读清楚被拒绝的命令和目标路径，确认不是路径过宽、权限过大或删除操作。

## `/local`、`/cloud` 和 `/cloud-environment`

```text
/local
/cloud
/cloud-environment
```

### 适合本地的情况

- 需要本机文件或未提交改动；
- 需要本地浏览器、dev server 或私有网络；
- 需要使用本机已经安装的工具；
- 需要立即观察修改后的界面。

### 适合云端的情况

- 任务可以在隔离环境中完成；
- 不依赖本机未提交文件和特殊凭证；
- 想让它脱离本机继续运行；
- 想并行启动多个相对独立的任务。

切换执行位置后，重新确认项目、分支、依赖和可访问文件。不要默认“聊天历史同步了，所以本地文件也同步了”。

## `/worktree`

```text
/worktree
```

它适合隔离实验、并行任务和需要独立 Git 分支的工作。开始前确认：

- 依赖安装是否会写入共享位置；
- dev server 端口是否冲突；
- 最终改动如何合并回主分支；
- 是否包含未提交资源。

## 一个推荐的执行模板

```text
/status
/plan

目标：修复登录页在移动端的布局问题。
约束：不要改变 API，不要删除现有测试。
证据：复现步骤是……，相关文件是……。
完成条件：pnpm test、pnpm build 通过，移动视口不再横向溢出。
未知处理：如果无法确认设计意图，停下来询问，不要自行补设计。
```

这个模板比只写“帮我修一下”更可靠，因为它同时给了目标、范围、证据、约束和验证标准。
